vcore_perm 설계 리뷰

RVV permutation 클러스터 9개 모듈 1,565줄과 테스트벤치 437줄을 읽고 RVV 1.0 스펙 원문과 조항별로 대조했다. 구조는 정상이다. decode → issue FIFO → sequencer → VRF request → core → pipe → WB 흐름이 일관되고, 그룹 버퍼로 LMUL>1 교차 레지스터 접근을 푸는 방식도 맞다. 찾은 결함 11건은 전부 고쳤고, 회귀 테스트를 먼저 넣어 재현을 확인한 뒤 수정했다 — 수정 전 21개 실패 → 수정 후 56개 전부 통과.

구조

7단 elastic 체인, 한 번에 beat 하나

모든 단이 valid/ready 핸드셰이크로 연결된다. 눈여겨볼 것은 WB에서 sequencer로 돌아가는 seq_ack 되먹임이다 — 이것 때문에 명령어 하나의 beat들이 완전히 직렬화된다. 앞 beat가 VRF에 써질 때까지 다음 beat의 uop이 나가지 않는다.

모듈별 설명

9개 모듈이 각각 맡은 것

vcore_perm_pkg.sv248줄 · 타입 + 분류 함수

타입 6종과 분류 함수 11개. 이 파일의 핵심은 타입이 아니라 함수다 — vpop_needs_group_buf, vpop_vs2_is_mask_src, vpop_is_mask_dest, vpop_single_beat 같은 술어가 나머지 모듈 전체의 분기 조건이 된다. 새 명령어를 추가할 때 손댈 곳이 여기 한 군데로 모여 있어서 유지보수성이 좋다.

VCORE_VLEN=128 · MAXLMUL=8 · vpop_e 18종 · vcore_perm_ctrl_t가 전 단을 관통

vcore_perm_decode.sv242줄 · 조합회로

raw 32비트 명령어 → vcore_perm_decoded_t. funct6로 6개 그룹을 가르고 funct3로 form(VV/VX/VI)을 정한다. funct6=0x10과 0x14는 vs1 필드로 세부 명령어를 구분하는데, 특히 0x10에서 vs1≠0이면 vcpop.m/vfirst.m이므로 다른 클러스터로 넘기려고 일부러 거부한다 — 정확한 처리다.

합법성 검사 4종: vl ≤ VLMAX, 레지스터 정렬(beats 배수), vrgatherei16 인덱스 그룹 크기 ≤ MAXLMUL, vd/vs2 overlap.

주의: 정렬 검사가 그룹화되지 않는 마스크 오퍼랜드를 면제하는 로직이 들어 있다 (viota의 vs2, vcompress의 vs1, vmsbf류의 vd) — 이게 없으면 정상 명령어를 오탐한다

vcore_perm_issue_fifo.sv51줄 · depth 3

조합회로인 decode와 순차회로인 sequencer 사이의 탄성 버퍼. 순환 포인터 + 카운터의 교과서적 구현이고 flush_i도 올바르게 처리한다. DEPTH<2는 elaboration에서 $fatal.

vcore_perm_sequencer.sv103줄 · FSM 3상태

명령어 하나를 beat 여러 개로 펼친다. IDLE → SEND → WAIT_WB를 beat 수만큼 반복. beat마다 element_base(전역 원소 인덱스의 시작)와 레지스터 주소를 계산하는데, 주소 증가 규칙이 오퍼랜드 역할에 따라 다르다: 보통은 base + beat_index지만, 마스크 소스/목적지는 beat와 무관하게 고정이다.

read_vs1 / read_vs2 를 여기서 정해 내려보낸다 — vmv.v.*, vid.v, vmv.s.x는 vs2를 아예 읽지 않는다

vcore_perm_vrf_request.sv189줄 · FSM 12상태

1R1W 포트 하나로 필요한 소스를 순서대로 긁어온다. PRELOAD_VS2 → PRELOAD_VS1 → SRC2 → SRC1 → DST → EXEC. 이 모듈이 이 설계에서 가장 중요한 결정을 담고 있다 — gather/slide/compress는 첫 beat에서 vs2 EMUL 그룹 전체(최대 8개 레지스터)를 버퍼에 통째로 올린다. 그 뒤 beat들은 버퍼를 재사용한다.

vrgatherei16만 인덱스(vs1, EEW=16)용 두 번째 그룹 버퍼를 따로 쓴다. 인덱스의 EMUL이 데이터의 EMUL과 다를 수 있기 때문이다.

비용: 1024비트 × 2 = 2,048 플립플롭. dst_old를 항상 읽으므로 tail-undisturbed가 공짜로 성립한다

vcore_perm_core.sv357줄 · 순수 조합

데이터패스 본체. perm_lane() 함수가 출력 원소 하나를 계산하고, SEW별로 4개 분기에서 그 함수를 VLEN/SEW번 펼친다. 함수 마지막의 정책 체인(prestart → tail → v0 selector → predicate → 결과)이 모든 명령어에 공통 적용된다.

변수 폭 part-select를 쓰지 않으려고 fld_get/fld_get_wide(가변 시프트 + 고정 마스크)를 쓴 것은 올바른 판단이다 — Verilator와 합성 도구 모두 +: 폭이 상수여야 한다.

모든 런타임 인덱스가 사용 전에 범위 검사된다 (idx_safe) — X 전파와 배열 범위 초과를 구조적으로 막는다

vcore_perm_pipe.sv82줄 · 1-cycle latch

core를 감싸는 한 단 레지스터. rsp_slot_ready = !rsp_valid_q || rsp_ready_i로 슬롯이 비거나 이번 사이클에 비워질 때 새 요청을 받는다. ALU와 달리 VLEN을 상·하위로 쪼개지 않는데, 크로스바 라우팅은 절반씩 나눠서 이득이 없다는 판단이고 타당하다.

vcore_perm_wb.sv93줄 · FSM 3상태

결과를 VRF에 쓸지 스칼라 레지스터에 쓸지 meta_q.is_scalar로 가른다. 쓰기 후 WB_EVENT에서 TOP commit과 sequencer ack를 각각 독립적인 pending 비트로 관리해서, 둘 중 하나가 늦게 받아도 다른 하나가 막히지 않는다. 깔끔하다.

illegal이면 쓰기를 건너뛰고 바로 WB_EVENT로 — 잘못된 데이터가 VRF에 닿지 않는다

vcore_perm_top.sv126줄 · 배선

로직 없이 배선만. 외부 인터페이스는 VRF read 1, VRF write 1, scalar write 1, commit 1 — 상위 통합 시 붙일 지점이 명확하다.

타이밍

beat 하나에 드는 사이클

VRF 접근 하나가 REQ+RSP 2사이클이다. 여기에 EXEC 1, WRITE 1, EVENT 1이 붙는다. 그룹 버퍼를 쓰는 명령어는 첫 beat에서만 그룹 레지스터 수 × 2사이클을 추가로 낸다.

포트 경쟁

1R1W에서 permutation이 정말 밀리는가

"permutation은 소스를 많이 읽으니 공유 1R1W 포트에서 불리하다"는 통념이 이 설계에 맞는지 실측했다. 측정 단위는 원소 하나당 VRF 포트 트랜잭션 수(read 요청 + write)다 — 공유 포트에서 경쟁의 화폐는 이것이다. 기준선은 vmerge.vvm으로 잡았다. 3-오퍼랜드 마스크 연산이라 vadd.vv와 구조가 같다.

통념이 이 설계에는 맞지 않는다. permutation이 평범한 3-오퍼랜드 연산보다 포트를 덜 쓴다. 이유는 그룹 버퍼다 — 순진한 구현은 beat마다 소스 그룹을 다시 읽어 O(LMUL²)가 되지만, 여기는 명령어당 한 번만 읽어 O(LMUL)다. LMUL=8이면 그 차이가 64 read 대 8 read다. 흔히 밟는 함정을 이미 피해 갔다.

측정하다 찾은 낭비 — 죽은 dst_old 읽기

모든 beat가 이전 목적지 레지스터를 읽고 있었다. 필요한 경우는 정해져 있다 — prestart 구간, vta=0인 tail, vma=0인 비활성 원소, vslideup의 offset 아래 구간. vstart=0·vl>0·unmasked·vta=1이면 beat의 모든 레인이 덮어써지므로 그 읽기는 순수한 포트 낭비다. vid.v가 극단적인 예였다 — 소스가 없는 명령어인데 beat당 1 read를 쓰고 있었다.

핵심 아이디어

그룹 버퍼와 전역 인덱스

LMUL>1에서 permutation이 어려운 이유는 목적지 beat 하나를 만드는 데 소스 그룹의 아무 레지스터나 필요할 수 있다는 점이다. vrgather의 인덱스가 어디를 가리킬지 모르고, vslideup의 offset이 레지스터 경계를 몇 개든 넘을 수 있다. 이 설계는 소스 그룹 전체를 먼저 버퍼에 올려 이 문제를 없앤다.

결함 11건 — 스펙 조항, 재현, 수정

각 항목은 RVV 1.0 원문(v-spec.adoc) 조항과 대조해 확정했고, 먼저 실패하는 테스트를 TB에 넣어 재현을 확인한 뒤 고쳤다. 아래 FIXED 배지 옆 테스트 이름이 그 회귀 테스트다.

데이터 오류F1FIXED회귀: F1 vcompress ignores mask bits past vl

vcompress가 vl 너머의 마스크 비트까지 센다

RVV는 vcompress를 vl 미만 원소에 대해서만 정의한다. 이 구현은 popcount와 소스 탐색을 둘 다 group_size(= VLMAX)로 끊는다. vl < VLMAX인데 마스크에 vl 이상 위치의 비트가 서 있으면 그 원소까지 압축 대상이 된다.

vcore_perm_core.sv:188 (탐색 루프) · vcore_perm_core.sv:308,319,330,341 (total_count)

// 현재
for (k = 0; k < VLEN; k++)
  if (64'(k) < group_size && src1[k]) begin ... end
// total_count 도 동일
if (64'(k) < 64'(ctrl_i.group_regs)*64'(VLEN/8) && src1_i[k]) total_count++;

// 스펙: 둘 다 vl 로 끊어야 한다
if (64'(k) < 64'(ctrl.vl) && src1[k]) begin ... end
재현

SEW=32, LMUL=1(VLMAX=4), vl=2, vs1 = 0b1100. 스펙은 활성 원소가 0개이므로 vd에 아무것도 쓰지 않는다. 이 구현은 원소 2·3을 vd[0]·vd[1]로 압축해 넣는다.

데이터 오류F2FIXED회귀: F2 / F2b vrgather·vslidedown out-of-VLMAX → 0 (mf2)

fractional LMUL에서 VLMAX가 데이터패스에 전달되지 않는다

decode는 vlmul이 101/110/111일 때 fraction_div를 계산해 vl 합법성 검사에만 쓰고 버린다. ctrl 구조체에는 group_regs만 실려 나가고 그 값은 1이다. core는 group_size = group_regs × (VLEN/SEW)를 VLMAX로 간주하므로, fractional LMUL에서 VLMAX를 실제보다 최대 8배 크게 본다.

RVV는 "인덱스 ≥ VLMAX면 0", "slidedown이 VLMAX를 넘겨 읽으면 0"이라고 규정한다. 이 구현은 그 구간에서 레지스터에 남아 있던 이전 값을 읽는다.

vcore_perm_decode.sv:155–164 (fraction_div, 밖으로 안 나감) · vcore_perm_core.sv:118 (group_size) · vcore_perm_pkg.sv:39–52 (ctrl에 LMUL 필드 없음)

재현

vsetvli t0, x0, e32, mf2, ta, ma → VLMAX=2. v1의 네 슬롯에 10,20,30,40을 넣고 vrgather.vi v2, v1, 3. 스펙은 0, 이 구현은 40을 쓴다.

고치는 법

vcore_perm_ctrl_t에 vlmax(또는 fraction_div) 필드를 하나 추가하고 core의 group_size를 그 값으로 바꾸면 끝난다. decode는 이미 계산해 두고 있다.

데이터 오류F3FIXED회귀: F3 / F3b viota·vmsbf vd/vs2 overlap illegal

viota.m의 vd / vs2 overlap 검사가 없다

decode의 overlap 검사 unique case에 gather·slide·compress는 있는데 VPOP_VIOTA가 없다. viota는 vs2가 고정이고 vd는 beat마다 증가하므로, vd가 vs2를 덮으면 beat 0의 쓰기가 마스크 소스를 파괴하고 beat 1부터 잘못된 값을 센다.

RVV 1.0 §15.2도 "목적지 레지스터 그룹은 소스 레지스터와 겹칠 수 없다"고 명시한다 — 즉 illegal로 거부해야 맞다.

vcore_perm_decode.sv:212–228 (case에 VPOP_VIOTA 항목 없음)

재현

LMUL=2에서 viota.m v2, v2. beat 0이 v2를 결과로 덮어쓰고, beat 1이 그 덮인 v2를 마스크로 다시 읽는다.

같은 규칙이 vmsbf/vmsof/vmsif에도 있지만, 이쪽은 단일 beat라 읽기가 쓰기보다 먼저 끝나서 결과는 맞다. 그래도 스펙상으로는 거부해야 하는 인코딩이다.

스펙 위반F4FIXED회귀: F4 / F4b / F4c slidedown 허용, slideup 거부 유지

vslidedown / vslide1down을 과잉 거부한다

RVV 1.0은 overlap을 vslideup과 vslide1up에만 금지한다. slidedown 계열에는 그런 제약이 없다 — 낮은 인덱스로 당겨오는 방향이라 in-place가 안전하기 때문이다. 이 구현은 네 가지를 한 묶음으로 거부한다.

vcore_perm_decode.sv:217 — VPOP_VSLIDEDOWN, VPOP_VSLIDE1DOWN을 case 목록에서 빼면 된다

게다가 이 마이크로아키텍처는 vs2 그룹 전체를 먼저 버퍼에 올린 뒤 목적지를 쓰기 때문에 overlap이 애초에 위험하지 않다. 제약을 걸 이유가 없다.

영향

vslidedown.vi v8, v8, 1은 컴파일러가 흔히 내는 정상 코드인데 illegal로 튕긴다.

스펙 위반F5FIXED회귀: F5 / F5b / F5c vstart≠0 illegal

vstart ≠ 0 에서 illegal 예외를 내지 않는다

vcompress.vm, viota.m, vmsbf/vmsof/vmsif.m은 RVV 1.0에서 vstart가 0이 아니면 illegal-instruction 예외를 내도록 규정돼 있다. 이 구현은 그냥 일반 prestart 규칙(vstart 미만은 undisturbed)을 적용한다.

vcore_perm_decode.sv — vstart를 ctrl로 넘기기만 하고 검사하지 않음 · vcore_perm_core.sv:232 (일반 prestart)

trap 후 재개(resumption) 시나리오에서 잘못된 결과가 나온다. decode에 if (vpop_requires_vstart_zero(op) && cmd_i.vstart != 0) operation_valid = 1'b0; 한 줄이면 해결된다.

스펙 위반F6FIXED회귀: F6 vslideup below-offset stays undisturbed

마스크된 vslideup에서 offset 아래 구간에 agnostic 채움이 들어간다

RVV는 vslideup의 0 ≤ i < OFFSET 구간을 undisturbed로 못 박는다. 이 구현은 computed = dst_old로 값을 맞춰 두지만, 그 뒤 공통 정책 체인이 "비활성 원소 + vma=1"을 만나면 ret.data = '1로 덮어쓴다.

vcore_perm_core.sv:145 (offset 아래 처리) → vcore_perm_core.sv:240–244 (정책 체인이 덮어씀)

재현 조건

vm=0, vma=1, offset>0, 그리고 offset 아래 위치의 v0 비트가 0. 셋이 동시에 성립할 때만 나타난다.

데이터 오류F7FIXED회귀: F7 / F7b 마스크 인지 스캔

마스크된 viota.m·vmsbf류가 비활성 원소까지 본다

core의 스캔은 global_index 미만의 모든 src2 비트를 센다. v0 마스크는 "이 원소에 쓸지 말지"에만 쓰이고 누적에는 관여하지 않는다.

vcore_perm_core.sv:207–209

스펙 원문으로 확정했다. §15.2: "This instruction can be masked, in which case only the enabled elements contribute to the sum." §15.1의 vmsbf도 "before the first active source element that is a 1"이라 같은 문제다 — 비활성 원소의 set 비트가 run을 끊으면 안 된다.

스펙 §15.2의 마스크 예제를 그대로 TB에 옮겨 확인했다 (v0=1110_1011, v2=1001_0001 → 결과 1 1 1 5 1 7 1 0). 수정 전에는 e5·e6·e7이 2로 나왔다 — 비활성인 e4의 set 비트를 셌기 때문이다.

고침 — vcore_perm_core.sv: viota 스캔과 vmsbf/vmsof/vmsif 스캔 양쪽에 (ctrl.vm || mask[k]) 게이트 추가

데이터 오류F9FIXED회귀: F9 / F9b vstart≥vl 완전 미갱신

vstart ≥ vl 인데 tail에 agnostic 값을 쓴다

RVV 1.0 §5.4: "When vstart ≥ vl, there are no body elements, and no elements are updated in any destination vector register group, including that no tail elements are updated with agnostic values."

정책 체인의 첫 분기가 prestart였기 때문에, vstart ≥ vl인 원소는 prestart를 지나 tail 분기로 떨어져 vta 채움을 받았다. vl=0이면 목적지 레지스터 전체가 all-ones가 된다 — 루프 말미에 흔히 나오는 상황이다.

고침 — vcore_perm_core.sv: 정책 체인 맨 앞에 if (ctrl.vstart >= ctrl.vl) 분기. vmv.x.s/vfmv.f.s는 스펙상 예외인데 애초에 lane 루프 밖에서 처리되므로 영향 없음

재현

vmv.v.i v8, 3를 vl=0, vta=1로. 스펙은 v8 불변, 수정 전에는 v8 전체가 FFFF…가 됐다.

데이터 오류F10FIXED회귀: F10 vrgather.vx 인덱스 미절단

vrgather.vx의 인덱스가 SEW로 잘린다

RVV 1.0 §16.4: "The index value in the scalar register and the immediate, zero-extended to XLEN bits, are treated as unsigned integers. If XLEN > SEW, the index value is not truncated to SEW bits."

구현은 .vx 인덱스를 broadcast_scalar가 만든 SEW 폭 벡터에서 꺼내 썼다. SEW=8이면 상위 24비트가 날아간다.

고침 — pkg에 ctrl.idx_from_scalar 추가, core의 VRGATHER 분기가 원시 32비트 scalar를 인덱스로 사용

재현

SEW=8(VLMAX=16), x[rs1] = 0x104(260). 8비트로 자르면 4 → 범위 안 → 엉뚱한 원소. 자르지 않으면 260 ≥ VLMAX → 0. 수정 전에는 원소 4의 값이 나왔다.

스펙 위반F11FIXED회귀: F11 vmv1r.v vstart≥evl

vmv<nr>r.v가 vstart ≥ evl 에서도 쓴다

RVV 1.0 §16.6: "The usual property that no elements are written if vstart ≥ vl does not apply to these instructions. Instead, no elements are written if vstart ≥ evl" (evl = NREG × VLEN/SEW). 구현은 vtype을 통째로 무시하느라 이 한 줄까지 무시했다.

고침 — decode가 VMVNR 경로에서 ctrl.vlmax에 evl을 넣고, core가 vstart < vlmax일 때만 복사

스펙 위반F12FIXED레퍼런스 대조가 발견

스칼라 이동 명령어가 LMUL>1에서 거부된다

RVV 1.0 §16.1: "The integer scalar read/write instructions ... ignore LMUL and vector register groups." 그런데 decode의 EMUL 정렬 검사(vd % beats == 0)가 vmv.x.s / vfmv.f.s / vmv.s.x / vfmv.s.f 에도 적용되고 있었다.

vmv.x.s의 vd 필드는 스칼라 rd라 정렬이라는 개념 자체가 없고, vmv.s.x의 vd는 벡터지만 단일 레지스터다. vmsbf/vmsof/vmsif는 마스크 오퍼랜드 면제로 이미 빠져 있었고 이 넷만 남아 있었다.

고침 — vcore_perm_decode.sv: 정렬 검사 전체를 vpop_single_beat(op) 명령어에서 면제

-      if (beats > 1) begin
+      if ((beats > 1) && !vpop_single_beat(decoded_o.ctrl.op)) begin
재현

LMUL=2에서 vmv.x.s x9, v0. rd=9가 2의 배수가 아니라서 illegal로 거부됐다. 컴파일러가 흔히 내는 코드다.

경미F8FIXED회귀: F8 / F8b / F8c reserved 인코딩 거부

reserved 필드를 검사하지 않는다

vmv.v.*와 vmv.s.x는 vs2 필드가 0이어야 하고, vmv.v.*·vmvNr.v·vmv.x.s는 vm이 1이어야 한다. 이 필드들은 다운스트림에서 쓰이지 않으므로 데이터가 틀리지는 않는다. reserved 인코딩이 조용히 정상 명령어로 실행될 뿐이다.

vcore_perm_decode.sv:88–128

잘 된 것

구조적으로 맞게 잡은 결정들

  • v0를 스냅샷으로 받는다. 마스크를 VRF 포트로 다시 읽지 않으니 v0 일관성 문제가 구조적으로 사라진다. 클러스터 경계를 잘 그었다.
  • 오퍼랜드 역할을 술어 함수로 분리했다. "이 오퍼랜드가 LMUL로 그룹화되는가"를 vpop_vs2_is_mask_src 같은 함수 한 곳에 모아 두고 sequencer·decode·core가 모두 그걸 본다. 마스크 오퍼랜드가 그룹화되지 않는다는, 놓치기 쉬운 규칙을 일관되게 처리한 이유가 여기 있다.
  • 런타임 인덱스를 전부 사용 전에 범위 검사한다. idx_safe 패턴 덕분에 아키텍처적으로 "죽은" 분기에서도 배열 범위를 벗어나지 않는다. X 전파와 시뮬-합성 불일치를 예방한다.
  • 가변 폭 part-select를 피했다. fld_get/fld_get_wide는 합성 가능성을 위해 필요한 우회다. 함수 인자는 상수로 취급되지 않는다는 점을 정확히 짚었다.
  • illegal이면 쓰기를 건너뛴다. WB가 illegal_op에서 WB_WRITE를 통째로 스킵하므로 잘못된 데이터가 VRF에 절대 닿지 않는다.
  • commit과 seq_ack의 pending 비트를 분리했다. TOP과 sequencer 중 한쪽이 느려도 다른 쪽이 막히지 않는다.
  • vrgatherei16의 인덱스 EMUL을 독립 계산한다. SEW<16일 때 인덱스 그룹이 데이터 그룹보다 커진다는 것을 알아채고 별도 버퍼와 별도 합법성 검사를 뒀다. 실제로 놓치기 쉬운 부분이다.
검증 현황

34개 전부를 골든 레퍼런스와 대조한다

"돌아간다"는 검증이 아니다. tb_vcore_perm_ref.sv는 스펙 문장에서 독립적으로 쓴 참조 모델을 두고, 매 케이스마다 VRF 32개 레지스터 전체와 스칼라 write를 비교한다 — 엉뚱한 레지스터에 쓰는 것까지 잡힌다.

모델은 RTL과 다른 표현을 쓴다. RTL은 1024비트 그룹 버퍼에서 shift/mask로 원소를 뽑지만 모델은 전역 원소 번호로 인덱싱하는 평평한 배열을 쓴다. RTL을 바꿔 말한 모델이었다면 같이 틀렸을 버그가 이 차이를 못 넘는다.

모델이 틀렸던 두 곳 (RTL은 정상)

처음 돌렸을 때 나온 실패 두 종류는 모델 쪽 버그였다. RTL이 맞았다는 확인이기도 해서 남겨 둔다.

  • fractional LMUL의 tail 범위. 모델이 tail을 VLMAX에서 끊었는데, 스펙 §5.4는 tail(x) = (vl ≤ x < max(VLMAX, VLEN/SEW))다. mf2/SEW32면 VLMAX=2지만 레지스터 슬롯은 4개고, 남는 2개도 tail이다.
  • simm5 부호확장. vmv.v.i·vmerge.vim의 5비트 즉치는 부호확장, vrgather.vi·vslideup.vi·vslidedown.vi는 영확장이다. RTL은 둘을 정확히 구분하고 있었다.

남은 것

  • flush_i가 모든 TB에서 상수 0이다. 모든 모듈에 flush 경로가 있는데 한 번도 동작시켜 보지 않았다. 남은 검증 공백 중 가장 크다 — 특히 그룹 preload 중간 flush와, WB가 pending 비트를 든 채 flush되는 경우.
  • mf4 / mf8. fractional 경로 자체는 mf2로 덮었다.
  • 명령어 간 hazard. sequencer가 한 번에 명령어 하나만 다루므로 현재 구조에서는 발생하지 않지만, 상위 통합 시 확인이 필요하다.
